# HU-05 - Endpoint: Consultar Permisos Dinámicamente

Como servicio de autorización,
quiero exponer un endpoint GET /api/permissions/users/{userId} que retorne dinámicamente los permisos de un usuario,
para que authentication-service pueda llenar el JWT sin hardcodear permisos.

## Historia de Usuario Enriquecida

### Contexto y Objetivo de Negocio
El servicio de autenticación consume internamente (vía Feign) el endpoint de consulta de permisos durante el login para obtener la lista actualizada de permisos del usuario y incluirla en el JWT. Esto desvincula la asignación de permisos de la lógica de autenticación y permite cambios dinámicos sin redeploy.

### Descripción Funcional Detallada
El endpoint GET /api/permissions/users/{userId} retorna la lista de permisos asignados a un usuario. La respuesta incluye userId, array de permisos (REPORT_READ, REPORT_DOWNLOAD, etc.) y timestamp. Si el usuario no existe, retorna 404. Si el usuario no tiene permisos, retorna 200 con array vacío. El endpoint es consumido internamente por authentication-service vía Feign Client, no es público.

### Ejemplos de Respuesta
**Respuesta exitosa (HTTP 200):**
```json
{
  "userId": 1,
  "permissions": ["REPORT_READ", "REPORT_DOWNLOAD"],
  "timestamp": "2026-05-14T10:30:00Z"
}
```

**Usuario sin permisos (HTTP 200):**
```json
{
  "userId": 2,
  "permissions": [],
  "timestamp": "2026-05-14T10:30:00Z"
}
```

**Usuario no encontrado (HTTP 404):**
```json
{
  "timestamp": "2026-05-14T10:31:00Z",
  "status": 404,
  "error": "Not Found",
  "message": "Usuario con ID 999 no encontrado",
  "path": "/api/permissions/users/999"
}
```

## Criterios de Aceptación
- [ ] Endpoint GET /api/permissions/users/{userId} expuesto y funcional.
- [ ] Retorna HTTP 200 con lista de permisos si usuario existe.
- [ ] Retorna HTTP 200 con lista vacía si usuario no tiene permisos.
- [ ] Retorna HTTP 404 si usuario no existe.
- [ ] La respuesta incluye userId, permissions array y timestamp.
- [ ] El endpoint es documentado como interno (OpenAPI con descripción "Uso interno").
- [ ] Validación: userId debe ser numérico > 0.

## Casos Límite y Validaciones
- Usuario con ID negativo: validar y rechazar con 400.
- Usuario con ID 0: validar y rechazar con 400.
- Usuario con ID muy grande: retornar 404 si no existe.
- Concurrencia: múltiples requests simultáneos al mismo usuario.

## Requisitos No Funcionales Relevantes
- Seguridad: Solo consumible internamente por authentication-service (documentar en OpenAPI).
- Rendimiento: Respuesta en < 100ms.
- Observabilidad: Registrar consultas con userId (sin datos sensibles).
- Disponibilidad: Si falla, authentication-service usa fallback (lista vacía).

## Requisitos de Testing
- Pruebas unitarias: Validación de entrada, formato de respuesta.
- Pruebas de integración: Consulta BD, usuarios con/sin permisos.
- Pruebas de contrato: Estructura response, códigos HTTP.

## Consideraciones Técnicas
- Backend: PermissionController, PermissionService, PermissionRepository.
- Anotaciones OpenAPI: @Operation, @ApiResponse, @SecurityRequirements() (vacío para indicar sin auth).
- DTO: UserPermissionsResponseDTO con userId, permissions[], timestamp.
- Transacción: ReadOnly.

## Sugerencia de Estructura Técnica
- Crear `PermissionController.getPermissions(@PathVariable Long userId)`
- Crear `PermissionService.getUserPermissions(Long userId)`
- Crear `UserPermissionsResponseDTO`
- Documentar en OpenAPI como endpoint interno (no público)
