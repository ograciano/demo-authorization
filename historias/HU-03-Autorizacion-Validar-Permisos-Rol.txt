HU-03 - Autorización de acceso por roles y permisos

Como sistema consumidor,
quiero validar si un usuario tiene permisos para ejecutar una acción,
para permitir o rechazar operaciones protegidas según sus roles y privilegios.

Objetivo técnico:
Implementar un backend de autorización en Java 17 con Spring Boot que valide roles y permisos asociados a un usuario autenticado.

Alcance funcional:
- Crear endpoint POST /api/authorization/check-permission.
- Recibir identificador de usuario, recurso y acción solicitada.
- Consultar roles del usuario.
- Consultar permisos asociados a los roles.
- Responder si el acceso está permitido o denegado.
- No realizar autenticación en este servicio; solo autorización.

Buenas prácticas esperadas:
- Separar autenticación de autorización.
- El servicio de autorización debe confiar en identidad previamente autenticada.
- Validar request con jakarta.validation.
- Usar respuestas explícitas: allowed true/false.
- Evitar exponer información interna de roles si no es necesario.
- Implementar logs de auditoría para accesos denegados.
- Manejar errores con formato estándar.
- Mantener estructura por capas: controller, service, repository, dto, entity.
- Diseñar permisos con formato recurso:acción, por ejemplo USER:READ, USER:CREATE, REPORT:DOWNLOAD.

Endpoint:
POST /api/authorization/check-permission

Headers:
Content-Type: application/json
Authorization: Bearer <jwt>

Ejemplo de entrada permitida:
{
  "userId": 1,
  "resource": "REPORT",
  "action": "DOWNLOAD"
}

Ejemplo de salida permitida HTTP 200:
{
  "allowed": true,
  "userId": 1,
  "resource": "REPORT",
  "action": "DOWNLOAD",
  "reason": "Permiso concedido por rol ADMIN"
}

Ejemplo de entrada denegada:
{
  "userId": 2,
  "resource": "REPORT",
  "action": "DELETE"
}

Ejemplo de salida denegada HTTP 200:
{
  "allowed": false,
  "userId": 2,
  "resource": "REPORT",
  "action": "DELETE",
  "reason": "El usuario no cuenta con el permiso requerido"
}

Ejemplo de salida con error HTTP 400:
{
  "timestamp": "2026-05-13T10:40:00",
  "status": 400,
  "error": "Bad Request",
  "message": "resource y action son obligatorios",
  "path": "/api/authorization/check-permission"
}

## Requisitos de OpenAPI/Swagger Desde el Inicio
- La anotación @Operation debe documentar el propósito del endpoint.
- La anotación @ApiResponse debe documentar respuestas 200, 400 con ejemplos.
- La anotación @SecurityRequirements() sin parámetros indica que el endpoint es público (no requiere JWT).
- La configuración de SecurityScheme en OpenApiConfig debe estar completada (type=HTTP, scheme=Bearer, format=JWT).
- El endpoint debe ser documentable en Swagger UI (/swagger-ui.html) sin errores de configuración.

Reglas de negocio:
- Un usuario puede tener uno o varios roles.
- Un rol puede tener uno o varios permisos.
- Si al menos un rol del usuario contiene el permiso requerido, el acceso debe permitirse.
- Si el usuario está inactivo, el acceso debe denegarse.
- Si el recurso o acción no existe, el acceso debe denegarse.

Criterios de aceptación:
1. Dado un usuario con rol que contiene el permiso requerido, cuando se valide la autorización, entonces allowed debe ser true.
2. Dado un usuario sin el permiso requerido, cuando se valide la autorización, entonces allowed debe ser false.
3. Dado un usuario inactivo, cuando solicite autorización, entonces allowed debe ser false.
4. Dado un request inválido, entonces el servicio debe responder HTTP 400.
5. El servicio debe registrar eventos relevantes de autorización para auditoría.

Sugerencia de estructura técnica:
- AuthorizationController
- AuthorizationService
- PermissionService
- UserRoleRepository
- RolePermissionRepository
- AuthorizationRequest
- AuthorizationResponse
- PermissionEntity
- RoleEntity
